# デプロイ先の検討

このスターターを複製して、複数のリポジトリで小さな Web アプリを増やすときの置き場所です。アプリの形（Next.js、NestJS、Prisma、PostgreSQL）は変えません。2026年11月時点の各社の枠で比べています。

## 結論

1 つのリポジトリは、次の単位で置きます。

- フロントとバックは Vercel の 1 プロジェクトにまとめる（Services）
- データベースは Neon の 1 プロジェクト

フロントだけ Vercel、バックを Render にする分け方は、この増やし方の初期の標準にはしません。Auth や Storage を Supabase に寄せるアプリ以外では、データベースは Neon にします。最初から全部を AWS に置くのは、いちばん後にします。

GitHub を Vercel に接続しただけでは、フロントとバックはまとまりません。ルートの `vercel.json` が Services で `apps/frontend` と `apps/backend` を 1 つのプロジェクトにします。`/persons` と Swagger の `/api` はバックエンドへ、それ以外はフロントへ送ります。画面と API は同じホストになるので、Vercel の `NEXT_PUBLIC_API_URL` は `/` にします。

Neon 用の設定ファイルはありません。Vercel の Marketplace から Neon をこのプロジェクトに接続すると、`DATABASE_URL`（プール）と `DATABASE_URL_UNPOOLED`（直接接続）が入ります。Vercel 上のインストールでは `apps/backend/scripts/vercel-prisma.js` が `prisma generate` のあと、直接接続があればそれで `prisma migrate deploy` します。プレビュー用の分岐は Preview だけをオンにします。ローカルと Docker はこれまでどおり `DATABASE_URL` と、起動前の `docker-entrypoint.sh` です。

待ち受けは `PORT`、無ければ `BACKEND_PORT`、それも無ければ 3001 です。Vercel は `PORT` を渡します。

## 検討の過程

### フロントとバックを同じ Vercel プロジェクトにする

Vercel は 2025年10月から、NestJS を設定ファイルなしで 1 つの Vercel Function（Fluid compute）として載せられます。これは Next.js と NestJS を 1 つのプロジェクトに合体させる機能ではありません。公式の NestJS のページも、NestJS アプリ単体のデプロイを説明しています。

2026年6月の Services（公開ベータ）で、1 つの Vercel プロジェクトに複数のフレームワークを置けるようになりました。`vercel.json` の `services` で `apps/frontend` と `apps/backend` を指定します。

プロジェクトを分けると、1 リポジトリで Vercel プロジェクトを 2 つ使います。Hobby のプロジェクト上限は 200 なので、分けたままではアプリ約 100 個で尽きます。Services で 1 つにまとめると約 200 個まで使えます。デプロイとプレビューも揃います。プロセスは別のままです。

Hobby の月間枠（Active CPU 4 時間、Function 呼び出し 100 万回など）はアカウント全体で共有です。個人の非商用が前提で、商用にするときは Pro（月 $20）です。この料金はプロジェクト数には比例しません。

NestJS を Function として動かす設定はリポジトリに入っています。待ち受けは `PORT` を優先し、Vercel のビルドで `prisma migrate deploy` を実行し、依存関係はリポジトリルートの lockfile で `npm ci` します。インスタンスが増減するので、実行時の `DATABASE_URL` はプール用を使います。1 リクエストの上限は Hobby で 300 秒です。常時接続や、プロセスの中で動き続ける処理には向きません。

### Render を初期の標準にしない

Render の無料 Web は、15 分操作がないと停止し、次のアクセスで約 1 分かけて起きます。無料のインスタンス時間はワークスペース全体で月 750 時間です。アプリを増やすとその時間を分け合うので、ほとんどのアプリが停止します。止めたくなければ有料の Web がアプリごとに月 $7 です。

Vercel はリクエストのあいだだけ動き、終われば課金も止まります。小さい API をたくさん置くなら、アイドル時の扱いは Vercel の方が合います。

Render に移すのは、そのうちの 1 つのアプリが常時起動、数分を超える処理、WebSocket のような常時接続を必要としたときです。NestJS は今の長時間プロセスのまま動かせます。

### データベースは Neon

PostgreSQL はアプリとは別に置きます。Vercel はデータベース本体をホストしません。

Neon の無料プランは、プロジェクトごとに 1 GB と月 100 CU 時間で、同じアカウントに 100 プロジェクトまで置けます。5 分操作がないと compute だけが止まり、データは残ります。リポジトリごとにデータベースを 1 つ足せます。

Supabase の無料プランは、同時に有効なプロジェクトが 2 つまで、データベースは 500 MB です。1 週間ほとんどクエリがないとプロジェクト自体が一時停止します。データは最大 1 年保持され、ダッシュボードから復帰できます。Auth、Storage、Realtime がセットになっているので、それらを使うアプリには向きます。このスターターは API を NestJS で持つので、データベースだけなら Neon を続けます。

100 プロジェクトを超えても、Launch に上げても上限は 100 のままです。101 個目以降は Scale（1,000 まで）です。使っていないプロジェクトを消して枠を空けるのが先です。複数アプリのデータベースを 1 つの Neon プロジェクトにまとめると、1 GB と 100 CU 時間を共有し、接続情報や復元も一緒になります。アプリごとにプロジェクトを分けます。

### AWS は後から、1 つのアプリだけ

AWS の新規アカウントは、最大 $200 のクレジットを 6 か月か使い切りの早い方まで使えます。クレジットのあと、小さな RDS は 1 つで月おおよそ $12 です。アプリの数だけデータベースを置くと、データベースだけで金額が積み上がります。ネットワークと権限の手順もリポジトリごとに増えます。

制限を超えたときは、先に Vercel と Neon の有料プランを続けます。AWS に移すのは、1 つのアプリが Vercel の Function では足りなくなったとき（常時接続、長い処理、専用ネットワーク）です。ほかのリポジトリは Vercel と Neon に残します。

仕事探しのためのインフラ経験としても、今はこのスターターの標準を AWS にしません。Vercel は GitHub へプッシュするとビルドと公開まで進み、サーバの台数、ネットワーク、証明書を自分で組みません。AWS で同じアプリを出すときに、VPC、サブネット、セキュリティグループ、IAM、ロードバランサー、コンテナの実行基盤、RDS、ログ、デプロイの経路を自分で決めると、それはインフラの設計と構築です。コンソールで一度起動しただけでは、その経験にはなりません。

見られ方には差があります。バックエンドや SRE の募集で AWS が前提なら、「Vercel と Neon にデプロイした」はアプリを出した経験であり、インフラを設計した経験としては扱われません。逆に、プロダクトを複数出した事実は、画面と API の開発としては残ります。Vercel と Neon でも、環境変数、プレビュー、ビルド時の migration、Function の時間制限、接続のプールは自分で扱います。

| | Vercel と Neon | AWS を自分で組む |
| --- | --- | --- |
| 手間 | リポジトリの接続、環境変数、`vercel.json` | ネットワーク、権限、DB、計算、ログ、デプロイ手順をアプリごとに用意する |
| 費用の性格 | 小さいアプリはアイドルでほぼ $0。枠か商用化で月 $20 前後から | 起動したままにすると、小さな構成でも月に数十ドル。止め忘れると請求が続く |
| 経験できること | Git 連携の公開、プレビュー、サーバーレスの制約、管理された Postgres | ネットワーク分割、最小権限、常駐プロセス、DB をプライベートに置く、障害時にログとメトリクスを見る |
| 経験しにくいこと | VPC、IAM、ロードバランサー、コンテナ基盤の設計 | 数分で次のアプリを公開する反復。アプリの数だけ同じ構成を手で繰り返すと、設計より作業になる |

経験が目的のときは、アプリを増やしている最中には移しません。1 つのアプリだけを、構成をコードで残し、予算の上限を付けて組む方が、「AWS でインフラを設計した」と言えます。それはこのスターターを量産する作業とは別にします。

## 今の最小構成で足りること

今の画面は、`Person` の一覧取得と登録だけです。この範囲は、Vercel にフロントとバックを置き、Neon に PostgreSQL を置くだけで成立します。ログイン、ファイル、定期実行はまだありません。

次を足すときは、Vercel と Neon のままにするか、その機能だけ別のサービスにするかをその時点で決めます。

| 足すもの | 今の構成のままでは足りない点 | 検討すること |
| --- | --- | --- |
| 認証 | ログインもセッションも無い | 認証は NestJS に置く。Services で画面と API が同じオリジンなら、Cookie をそのまま使える。ホストを分けるときは `FRONTEND_ORIGIN` と Cookie の送り方を合わせる。パスワードや OAuth の利用者管理を Supabase に任せるなら、データベースも Supabase に寄せる選択が戻ってくる。利用者管理だけを別サービスにし、データは Neon に残すこともできる |
| ファイル | Function に永続ディスクは無い。リクエスト本体のサイズにも上限がある | 画像や添付は Vercel Blob か、S3 のようなオブジェクトストレージに置く。データベースには保存先のキーだけを持つ |
| 長い処理、定期実行 | Hobby は 1 リクエスト最長 300 秒。プロセスはリクエストのあと残らない | 短い定期処理は、Vercel の Cron から NestJS のルートを呼ぶ。数分を超える処理や、待ち続けるワーカーは、そのアプリのバックエンドを Render に移す |
| 常時接続 | WebSocket のように接続を持ち続ける用途は、Function の向きではない | サーバから一方的に送るだけなら NestJS の SSE を先に検討する。双方向に持ち続けるなら、そのアプリだけ Render か AWS にする |
| プルリクエストごとのデータベース | プレビューのビルドが本番と同じ `DATABASE_URL` だと、確認用の migration が本番の表を変える | Neon のプレビュー用ブランチを Preview だけに有効にする。Production には作らない。migration の直接接続と、アプリが使うプール接続は分ける |
| 利用者の個人データ | 無料の Neon は、戻せる履歴が短く、停止中のバックアップも手厚くない | 個人情報や消えては困るデータを置く前に、有料プランの復元期間と、リージョンを本番の Function に合わせる。Vercel の既定リージョンは米国東部なので、日本向けなら実行リージョンと Neon のリージョンを揃える |
